================================================================================
                      THE BIG PICTURE
================================================================================

What is a Goroutine?
  → A lightweight, independently executing function, managed by the Go
    runtime - not an OS thread, but far cheaper
  → Launched with one word: go someFunc()
  → The Go runtime schedules many goroutines onto a much smaller number
    of real OS threads

Why Goroutines Matter:
  → Real programs wait on things constantly - network calls, file I/O,
    database queries
  → Goroutines let your program do other useful work while waiting,
    instead of blocking everything on one slow operation
  → This is how Go servers handle thousands of concurrent connections
    without thousands of OS threads

================================================================================
                 LAUNCHING A GOROUTINE
================================================================================

  go someFunc()      // returns immediately - does NOT wait

  package main

  import "fmt"

  func sayHello() {
      fmt.Println("Hello from the goroutine!")
  }

  func main() {
      go sayHello()
      // main() may return before sayHello() ever runs!
  }

  This is the #1 beginner trap: main() returning kills every goroutine
  still running. Exercise 1 shows this happening for real.

================================================================================
                 THE FIX: sync.WaitGroup
================================================================================

  var wg sync.WaitGroup

  wg.Add(1)              // BEFORE launching
  go func() {
      defer wg.Done()     // when the goroutine finishes
      fmt.Println("Hello from the goroutine!")
  }()

  wg.Wait()               // blocks until the counter hits 0

================================================================================
                 DATA RACES AND sync.Mutex
================================================================================

  Two goroutines touching the same variable, at least one writing it,
  with no synchronization = a DATA RACE. Results become unpredictable.

  counter++                          // ❌ NOT atomic - a race if shared

  mu.Lock()
  counter++                          // ✅ safe - only one at a time
  mu.Unlock()

  Catch races for real with:  go run -race main.go

================================================================================
                 GOROUTINE LEAKS
================================================================================

  A goroutine blocked FOREVER (e.g. sending on a channel nobody reads)
  is never garbage collected - it just sits there, consuming memory,
  for the life of the program.

  go func() { ch <- result }()   // leaks if nobody ever reads ch

  Always know how a goroutine will stop.

================================================================================
                    KEY CONCEPTS SUMMARY
================================================================================

1. GOROUTINES
   go someFunc() - lightweight, runtime-scheduled concurrent execution

2. CONCURRENCY vs PARALLELISM
   Concurrency = structure (dealing with many things). Parallelism =
   execution (doing many things at the same instant, needs multiple cores)

3. sync.WaitGroup
   Add before launching, Done (deferred) inside the goroutine, Wait to block

4. LOOP VARIABLE CAPTURE
   Safe per-iteration on Go 1.22+ (this project: go1.26.5) - no workaround needed

5. DATA RACES
   Unsynchronized concurrent access + at least one write = a race.
   go run -race catches it. sync.Mutex fixes it (full coverage: Level 23)

6. GOROUTINE LEAKS
   Blocked forever = never garbage collected. Always plan the exit.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Forgetting to wait for a goroutine
  go fmt.Println("hi")   // main() might exit first

✅ RIGHT
  wg.Add(1); go func() { defer wg.Done(); fmt.Println("hi") }(); wg.Wait()

---

❌ WRONG: Assuming the pre-1.22 loop variable sharing bug still applies
  for i := 0; i < 5; i++ {
      go func(i int) { fmt.Println(i) }(i)   // unnecessary on Go 1.22+
  }

✅ RIGHT (this project's go1.26.5): just use i directly, it's already safe
  for i := 0; i < 5; i++ {
      go func() { fmt.Println(i) }()
  }

---

❌ WRONG: Unsynchronized shared state
  counter++   // from multiple goroutines - a data race

✅ RIGHT
  mu.Lock(); counter++; mu.Unlock()

---

❌ WRONG: A goroutine with no way to stop
  go func() { ch <- result }()   // leaks if nobody ever reads ch

✅ RIGHT: give it a timeout, a done channel, or a context

================================================================================
                      QUICK FAQ
================================================================================

Q: Why did my goroutine's print statement never show up?
A: main() almost certainly returned before the scheduler ran it. This is
   exactly the bug Exercise 1 demonstrates and Exercise 2 fixes.

Q: Is a goroutine an OS thread?
A: No - it's much lighter weight. The Go runtime multiplexes many
   goroutines onto a smaller number of real OS threads.

Q: Do I need the "i := i" loop variable trick?
A: Not on this project's Go version (1.26.5), or any Go 1.22+. Each loop
   iteration already gets its own copy. See Level 11 and this level's
   README for the full history of why this used to matter.

Q: Does the race detector (-race) always work?
A: It requires cgo. It worked in this course's sandbox with real captured
   output - if it's unavailable in your environment, the exercises still
   show you the buggy, non-deterministic output without it.
