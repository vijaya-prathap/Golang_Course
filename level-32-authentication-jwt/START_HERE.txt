================================================================================
                      THE BIG PICTURE
================================================================================

What Is Authentication?
  → Proving who is making a request - and letting them prove it again
    without resending their password every time
  → Two building blocks: bcrypt (never store plaintext passwords) and
    JWT (a compact, signed way to say "this is user X" on every request)

Why This Matters:
  → Almost every real API needs to know who's calling before deciding
    what they're allowed to do
  → Level 27's middleware and Level 24's context are exactly the tools
    that make this practical in idiomatic Go

================================================================================
                 PASSWORDS: HASH, NEVER ENCRYPT
================================================================================

Encryption is two-way (reversible with a key) - wrong for passwords, because
anyone who steals the key AND the database gets every plaintext password.

Hashing is one-way - bcrypt hashes a password once, and later only compares
a NEW hash of a guess against the stored one. There's no key to steal that
undoes it.

  hash, _ := bcrypt.GenerateFromPassword(password, bcrypt.DefaultCost)
  err := bcrypt.CompareHashAndPassword(hash, candidate) // nil == match

Real, verified rejection error for a wrong password:

  crypto/bcrypt: hashedPassword is not the hash of the given password

================================================================================
                    JWT: SIGNED, NOT SEALED
================================================================================

A JWT is three base64url segments: header.payload.signature

  eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTQyIn0.dNflZCu...

The header and payload are only ENCODED - readable by anyone, no secret
needed. This was verified directly: decoding a real token's payload with
nothing but base64url, no secret involved, printed every claim in plain
JSON. NEVER put a secret inside a JWT's claims.

The signature is what the secret protects - it proves the header+payload
weren't altered since signing. It does NOT hide them.

================================================================================
                 VALIDATING: THREE REAL FAILURE MODES
================================================================================

  jwt.ParseWithClaims(token, claims, keyfunc)

  A tampered token (one signature character flipped):
    "token signature is invalid: signature is invalid"

  An expired token (exp in the past):
    "token has invalid claims: token is expired"

  A forged alg:none token (no signature at all):
    "unexpected signing method: none (only HMAC is accepted)"
    - REJECTED because the keyfunc hard-codes the accepted algorithm,
      never trusting the token's own header to decide.

================================================================================
                    AUTH MIDDLEWARE IN ONE PICTURE
================================================================================

  Authorization: Bearer <token>
        │
        ▼
  Missing/malformed? ──────────────► 401
        │
        ▼
  jwt.ParseWithClaims + keyfunc
        │
        ├─ bad signature / expired / bad alg ──► 401
        │
        ▼
  context.WithValue(ctx, claimsContextKey{}, claims)
        │
        ▼
  downstream handler reads r.Context().Value(claimsContextKey{})

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. PASSWORDS
   Hash with bcrypt, never encrypt. Auto-salted, deliberately slow.

2. JWT STRUCTURE
   header.payload.signature - encoded, not encrypted. Never put secrets
   in claims.

3. VALIDATION
   Always check signature, always check expiration, always pin the
   accepted algorithm yourself.

4. THE alg:none LESSON
   The verifier decides how to verify - never the token's own header.

5. MIDDLEWARE
   Extract Bearer token -> validate -> inject claims via context.WithValue
   with an unexported key type (Level 24's pattern).

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Assuming a JWT is encrypted
  "It's signed, so nobody can read the payload." - false, see above.

❌ WRONG: Skipping expiration checks
  Trusting a valid signature forever, ignoring exp.

❌ WRONG: Hardcoded/weak signing secrets
  var secret = []byte("secret123")

✅ RIGHT: Long, random secret from environment (Level 34 covers this)

❌ WRONG: Trusting the token's own alg header
  return lookupKeyFor(t.Header["alg"])

✅ RIGHT: Hard-code the accepted method type in your keyfunc

❌ WRONG: Plaintext or weakly-hashed passwords
  storePassword(password) or storePassword(sha256(password))

✅ RIGHT: bcrypt.GenerateFromPassword

================================================================================
                      QUICK FAQ
================================================================================

Q: Is a JWT encrypted?
A: No. Header and payload are base64url-encoded, decodable by anyone with
   no key. Only the signature needs the secret, and it proves integrity,
   not secrecy.

Q: Why bcrypt instead of a fast hash like SHA-256?
A: Fast hashes let attackers try billions of password guesses per second
   against a stolen hash. bcrypt is deliberately slow and auto-salts.

Q: Can I revoke a JWT before it expires?
A: Not natively - the biggest JWT tradeoff versus sessions. Mitigate with
   short expirations plus the refresh-token pattern (Section 9 of README).

Q: What was the alg:none vulnerability?
A: A verifier that trusted the token's own "alg" header could be tricked
   into accepting an unsigned, attacker-edited token. Fix: the verifier,
   not the token, decides the accepted algorithm - always.
