================================================================================
                      THE BIG PICTURE
================================================================================

What is Repository-Service-Handler?
  → A way of splitting a program into three layers, each with ONE job:
      Repository - talks to storage, nothing else
      Service    - enforces business rules, nothing else
      Handler    - translates HTTP in and out, nothing else

Why It Matters:
  → A tangled "everything in one handler function" program can't be
    tested without a real database and a real HTTP server
  → Splitting the layers means each one can be tested, changed, and
    understood independently
  → Go's implicit interface satisfaction (Level 15) makes this easy to
    wire up with zero frameworks

================================================================================
                 THE THREE LAYERS
================================================================================

1. REPOSITORY (data access only)

  type UserRepository interface {
      Create(u User) error
      Get(id string) (User, error)
      Update(u User) error
      Delete(id string) error
  }

  type InMemoryUserRepository struct { /* map + mutex */ }
  // satisfies UserRepository IMPLICITLY - Level 15 revisited

2. SERVICE (business rules only, depends on the INTERFACE)

  type UserService struct {
      repo UserRepository // never the concrete type!
  }

  func (s *UserService) CreateUser(u User) error {
      if strings.TrimSpace(u.Name) == "" {
          return ErrInvalidName // rejected BEFORE touching the repository
      }
      return s.repo.Create(u)
  }

3. HANDLER (HTTP translation only, depends on the Service)

  type UserHandler struct {
      service *UserService
  }

  func (h *UserHandler) CreateUser(w http.ResponseWriter, r *http.Request) {
      var u User
      json.NewDecoder(r.Body).Decode(&u)
      if err := h.service.CreateUser(u); err != nil {
          http.Error(w, err.Error(), statusFor(err))
          return
      }
      json.NewEncoder(w).Encode(u)
  }

================================================================================
                 DEPENDENCY DIRECTION
================================================================================

  Handler --> Service --> Repository (interface)
                                 ▲
                    implemented by InMemoryUserRepository

The interface is defined where it's USED (in the Service's code), not
where it's implemented (the Repository package) - Level 15's Rule 3,
applied to a whole architecture.

================================================================================
                 WHY THIS MAKES TESTING EASY
================================================================================

Because the Service depends on an INTERFACE, tests can hand it a fake:

  type alwaysErrorRepository struct{}
  func (alwaysErrorRepository) Create(User) error { return errStorageDown }
  func (alwaysErrorRepository) Get(string) (User, error) {
      return User{}, errStorageDown
  }

  service := NewUserService(alwaysErrorRepository{})
  // now you can prove the Service handles a storage failure correctly -
  // with ZERO real storage involved

================================================================================
                 ERROR TRANSLATION ACROSS LAYERS
================================================================================

  Repository:  ErrNotFound (wrapped with %w)
       ↓
  Service:     passes it through, or returns its own business error
               (ErrInvalidName, ErrEmailTaken)
       ↓
  Handler:     the ONLY layer that knows what an HTTP status code is

  statusFor(err error) int {
      case errors.Is(err, ErrInvalidName): return 400
      case errors.Is(err, ErrEmailTaken):  return 409
      case errors.Is(err, ErrNotFound):    return 404
      default:                              return 500
  }

================================================================================
                    KEY CONCEPTS SUMMARY
================================================================================

1. THE THREE LAYERS
   Repository (data), Service (rules), Handler (HTTP) - one job each.

2. DEPENDENCY DIRECTION
   Handler -> Service -> Repository interface. Never the reverse.

3. INTERFACE OWNERSHIP
   Defined where it's used (the consumer's package), not where it's
   implemented.

4. TESTING
   Fakes at every boundary - no real storage or network needed anywhere.

5. ERROR TRANSLATION
   errors.Is at every boundary; only the Handler knows about status codes.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Service depends on a concrete repository type
  type UserService struct { repo *InMemoryUserRepository }

✅ RIGHT: Service depends on the interface
  type UserService struct { repo UserRepository }

---

❌ WRONG: Validation logic living in the Handler
  if u.Name == "" { http.Error(w, "name required", 400); return }

✅ RIGHT: Handler delegates to the Service, which owns validation
  if err := h.service.CreateUser(u); err != nil { ... }

---

❌ WRONG: Repository returning HTTP status codes
  func (r *InMemoryUserRepository) Get(id string) (User, int, error)

✅ RIGHT: Repository returns a plain error; the Handler decides the status
  func (r *InMemoryUserRepository) Get(id string) (User, error)

                      QUICK FAQ
================================================================================

Q: Why in-memory storage instead of Level 29's SQL setup?
A: This level is about the ARCHITECTURE, not the storage technology.
   In-memory storage keeps every exercise offline and fast, and proves
   the whole point: the Repository interface could be backed by SQL,
   memory, or anything else, and the Service/Handler would never know.

Q: Isn't this overkill for a simple CRUD app?
A: For a truly tiny program, yes - see "When This Is Overkill" in
   README.md. It earns its keep once business logic, testability, or
   swappable storage genuinely matter.

Q: Where does the Repository interface live?
A: In the Service's package (or wherever it's consumed) - Level 15's
   Rule 3. The repository package just exports concrete types.

Q: How is this different from Level 31 (Dependency Injection)?
A: It isn't fundamentally different - wiring everything by hand in
   main() IS dependency injection. Level 31 names the pattern and shows
   how to scale it past three layers.
