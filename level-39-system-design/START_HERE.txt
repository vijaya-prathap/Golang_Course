Welcome to Level 39! You've mastered production debugging (Level 38) - finding
out why a RUNNING system is misbehaving. Now it's time to learn SYSTEM DESIGN -
how to design a system so it holds up at scale and fails gracefully in the
first place, before an incident ever happens.

This level is more architectural than hands-on coding. Some topics (caching,
rate limiting, circuit breakers) have real, runnable Go code you'll write and
verify yourself. Others (database sharding, load balancer choice, message
queue selection) are judgment calls about tradeoffs - there's no compiler
error for picking the wrong one, so this level teaches you to reason about
them with diagrams and worked scenarios instead of pretending there's an
"output" to run.

================================================================================
                      THE BIG PICTURE
================================================================================

What Is System Design?
  → Reasoning about how a system (not just one function) behaves under
    real traffic, real growth, and real failures
  → The layer of thinking ABOVE correct code: your code can be flawless
    and the system can still fall over if nobody designed for scale
    and failure

Why It Matters:
  → Almost every level before this one asked "does this work correctly
    once?" System design asks "does it keep working when 10,000 people
    hit it at once, and what happens when a dependency goes down?"
  → This is the last conceptual leap before Level 40 (Real-World
    Projects) has you build complete systems using everything you know

================================================================================
                 SCALABILITY: THE CORE FORK IN THE ROAD
================================================================================

VERTICAL (scale up): bigger machine. Simple, but has a ceiling and is a
single point of failure.

HORIZONTAL (scale out): more machines. No ceiling, but needs a load
balancer and needs the service to handle shared state correctly.

THE KEY DETAIL: stateless services (no per-client data in server memory -
think JWTs, Level 32) scale horizontally almost for free. Stateful
services (server-side sessions) need sticky routing or a shared store
just to survive having more than one instance.

================================================================================
                    A SIMPLE EXAMPLE: TOKEN-BUCKET RATE LIMITING
================================================================================

package main

import (
    "fmt"
    "sync"
    "time"
)

type TokenBucket struct {
    mu         sync.Mutex
    capacity   float64
    tokens     float64
    refillRate float64
    lastRefill time.Time
}

func (b *TokenBucket) Allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    now := time.Now()
    b.tokens += now.Sub(b.lastRefill).Seconds() * b.refillRate
    if b.tokens > b.capacity {
        b.tokens = b.capacity
    }
    b.lastRefill = now
    if b.tokens >= 1 {
        b.tokens--
        return true
    }
    return false
}

Output (capacity 3, refill 5/sec, 5 requests back-to-back):
  Request 1: allowed=true
  Request 2: allowed=true
  Request 3: allowed=true
  Request 4: allowed=false
  Request 5: allowed=false

Three tokens allow a burst of three; the bucket runs dry and denies the
rest until it refills. This is real, executed Go code - see README.md
Section 4 for the full program and EXERCISES.md Exercise 3 to build it
yourself.

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. THE MINDSET SHIFT
   "Does it work?" -> "Does it hold up at scale, and fail gracefully?"

2. SCALABILITY
   Vertical (bigger machine) vs horizontal (more machines). Stateless
   services scale horizontally far more easily than stateful ones.

3. CACHING
   Cache-aside (lazy, most common) vs write-through (always fresh, costs
   more per write). A real LRU-ish cache with verified eviction.

4. RATE LIMITING
   Token bucket allows bursts, then smooths to a steady rate. A real,
   verified implementation - and a sliding-window alternative in the
   bonus challenges.

5. LOAD BALANCING
   Round-robin (simple, blind to load), least-connections (adapts to
   load), consistent hashing (key-to-backend stickiness).

6. DATABASE SCALING
   Read replicas scale reads; sharding scales writes/data volume at real
   operational cost. Connection limits are a SHARED budget across every
   instance.

7. MESSAGE QUEUES
   In-process channels suffice for in-process fan-out. Real queues
   (Kafka/RabbitMQ/SQS) earn their cost for cross-service fan-out and
   crash durability.

8. CIRCUIT BREAKERS
   Closed (normal) -> Open (fail fast after N failures) -> Half-Open
   (one trial call) -> Closed or back to Open.

9. MONOLITH VS MICROSERVICES
   Start as a well-layered monolith. Extract services only on a
   measured need for independent scaling or deployment - not by default.

10. THE CASE STUDY
    A URL shortener ties every concept together, end to end - exactly
    the shape of project Level 40 has you build for real.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Adopting microservices before there's a scaling or team-autonomy
   problem they actually solve.

✅ RIGHT: Start as a well-layered monolith (Level 30's pattern). Extract
   a service only on a measured need.

---

❌ WRONG: Adding a cache with no invalidation strategy ("it'll refresh
   eventually").

✅ RIGHT: Invalidate explicitly on write, with a short TTL as a backstop.

---

❌ WRONG: Shipping a public endpoint with no rate limit.

✅ RIGHT: Rate-limit every public endpoint before it ships.

---

❌ WRONG: Scaling application instances without checking whether
   instances × SetMaxOpenConns still fits the database's max_connections.

✅ RIGHT: Treat the database's connection ceiling as a shared budget
   across every instance.

---

❌ WRONG: Designing for scale you don't have yet - sharding and a
   microservice per feature for a service handling 50 requests/minute.

✅ RIGHT: Build the simplest design that meets today's real requirements.

================================================================================
                      QUICK FAQ
================================================================================

Q: Why does this level mix code and "design exercises" with no code?
A: System design genuinely is a mix. Caching, rate limiting, and circuit
   breakers reduce to real, testable Go code - so this level writes and
   runs that code for real. Database sharding strategy or monolith vs
   microservices are judgment calls about tradeoffs with no single
   correct output - so this level teaches you to reason about those with
   diagrams and worked scenarios instead of faking an "output."

Q: Do I need to install Kafka or RabbitMQ for this level?
A: No. Message queues are covered conceptually and by name (Section 7),
   since a meaningful example needs an actual running broker. The
   in-process channel pattern (Level 21) is what gets implemented.

Q: Should I default to microservices for a new project?
A: No - Section 9 argues against this directly. Start as a well-layered
   monolith and extract services only when there's a measured need.

Q: How is this different from Level 38 (Production Debugging)?
A: Level 38 diagnoses why a RUNNING system is misbehaving. Level 39
   designs the system BEFORE it's misbehaving, so it holds up and fails
   gracefully in the first place.
