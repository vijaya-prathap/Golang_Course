================================================================================
                      THE BIG PICTURE
================================================================================

What's a Module?
  → A versioned unit of one or more packages, described by one go.mod
  → "go mod init <path>" creates it
  → A package is the unit of organization INSIDE a module; a module is
    the unit of versioning and distribution

Why This Level Matters:
  → Real software is built from many modules, not one
  → Knowing go.mod, module commands, internal/, and API design is what
    separates "a script that runs" from "a project other code can depend on"

Key Insight:
  → A replace directive (or a go.work file) lets you develop two modules
    together on your own disk, before either is ever published anywhere

================================================================================
                    go.mod ANATOMY, AT A GLANCE
================================================================================

  module example.com/widgets     <- identity + import-path prefix
  go 1.26                        <- minimum language version
  require example.com/x v1.2.0   <- a dependency, pinned to a version
  replace example.com/x => ../x  <- redirect x locally (main module only)
  exclude example.com/x v1.0.0   <- blacklist a version (main module only)

================================================================================
                 WIRING TWO LOCAL MODULES, OFFLINE
================================================================================

  $ go mod edit -require=example.com/greetings@v0.0.0-00010101000000-000000000000
  $ go mod edit -replace=example.com/greetings=../greetings
  $ go run .
  Hello, Gopher!

No network call happens anywhere in that sequence - "replace" redirects
straight to the local directory.

================================================================================
                 internal/: A COMPILER-ENFORCED BOUNDARY
================================================================================

  example.com/owner/internal/secret   <- importable only from code rooted
                                          at example.com/owner (internal's
                                          parent)

Try it from a different module and the compiler refuses, even with a
replace directive pointing right at it:

  main.go:6:5: use of internal package example.com/owner/internal/secret
  not allowed

================================================================================
                 PACKAGE API DESIGN, IN ONE LINE
================================================================================

  Small, cohesive packages, named for what they DO, with the smallest
  exported surface that does the job, and no import cycles - ever.

================================================================================
                 go.work: DEVELOPING MODULES TOGETHER
================================================================================

  $ go work init
  $ go work use ./greetings ./app
  $ go run ./app                <- no require/replace needed between them!

go.work is usually a local, uncommitted file - it points at directories
specific to your own checkout, not something to share like go.mod.

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. go.mod
   module, go, require, replace, exclude - what each line means and does

2. SEMANTIC VERSIONING
   v0 promises nothing, v1 promises compatibility within v1, v2+ needs
   its own /vN import-path suffix

3. MODULE COMMANDS
   go mod tidy, go list -m all, go mod why, go mod graph

4. internal/
   Compiler-enforced visibility, scoped to the parent of "internal" -
   cannot be bypassed with replace or go.work

5. API DESIGN
   Cohesion, minimal exported surface, no circular imports

6. go.work
   The cleaner tool for actively developing several local modules together

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Committing a replace pointing at a path only you have
  replace example.com/x => /Users/yourname/dev/x

✅ RIGHT: Keep local-only replace paths uncommitted, or use go.work instead

---

❌ WRONG: A breaking v2 release that keeps the v1 module path
  module example.com/widgets           (should be .../widgets/v2)

✅ RIGHT
  module example.com/widgets/v2

---

❌ WRONG: Trying to import someone else's internal/ package
  import "example.com/owner/internal/secret"   (from a different module)

✅ RIGHT: There is no workaround - ask for it to be exported instead

---

❌ WRONG: One catch-all "utils" package that absorbs everything forever

✅ RIGHT: Small, focused packages named for what they do
  package dateutil / package mathutil / package validate

                      QUICK FAQ

Q: Why does this level avoid go get entirely?
A: So every exercise works offline. A replace directive (or go.work) points
   a module at a local directory instead of a network registry.

Q: What's the difference between replace and go.work?
A: replace lives in go.mod, is usually committed, and only affects the main
   module's own build. go.work is a separate, usually-uncommitted file that
   lets several local modules resolve each other with no require/replace
   needed between them.

Q: Can replace or go.work make an internal/ package importable from outside
   its module tree?
A: No. They only make a package findable on disk - internal/ visibility is
   enforced by the compiler and cannot be bypassed either way.

Q: Do I need a real v2 module to understand the /v2 import-path rule?
A: No - it's explained conceptually, since it can't be demonstrated with a
   real published module offline. Just recognize it when you see it.
