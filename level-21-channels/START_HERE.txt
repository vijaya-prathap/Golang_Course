================================================================================
                      THE BIG PICTURE
================================================================================

What is a Channel?
  → A typed conduit for sending and receiving values between goroutines
  → Not just a data pipe - its blocking rules are how goroutines SYNCHRONIZE
  → Go's answer to "how do two goroutines hand off a value safely?"

Why Channels Matter:
  → Level 20 gave you concurrency (goroutines) but left coordination to you
  → A shared variable + mutex works, but you must remember to lock every
    single access - forget once and you have a data race
  → A channel moves ownership of the value itself - once sent, only one
    goroutine has it at a time, with nothing left to "protect"

================================================================================
                 UNBUFFERED VS BUFFERED CHANNELS
================================================================================

1. UNBUFFERED (make(chan int)) - capacity 0

  ch := make(chan string)
  go func() { ch <- "hi" }()
  msg := <-ch
  // the send blocks until the receive is ready, and vice versa -
  // they must "rendezvous" at the same instant

2. BUFFERED (make(chan int, n)) - capacity n

  ch := make(chan int, 3)
  ch <- 1   // does NOT block - buffer has room
  ch <- 2   // does NOT block
  ch <- 3   // does NOT block - buffer now FULL
  ch <- 4   // WOULD block - no room until something receives

================================================================================
                    CLOSING CHANNELS & comma-ok
================================================================================

  close(ch)  → signals "no more sends, EVER"

  v, ok := <-ch
  // ok == true  -> v is a real value that was sent
  // ok == false -> channel is closed AND drained; v is the zero value

  Sending on a closed channel PANICS:
    panic: send on closed channel

  Closing an already-closed channel ALSO PANICS:
    panic: close of closed channel

================================================================================
                 range: THE IDIOMATIC CONSUMER LOOP
================================================================================

  for v := range ch {
      // receives values in send order
      // exits automatically once ch is closed AND drained
  }

  If the producer never calls close(ch), this loop blocks FOREVER after
  the last value - always defer close(ch) in the producer.

================================================================================
                 CHANNEL DIRECTION TYPES
================================================================================

  chan<- int   → send-only    (can only do ch <- v)
  <-chan int   → receive-only (can only do v := <-ch)

  func produce(out chan<- int) { out <- 1 }   // caller knows: only sends
  func consume(in <-chan int) int { return <-in } // caller knows: only receives

  Misusing this is a COMPILE ERROR, not a runtime bug - the compiler
  catches it before the program ever runs.

================================================================================
                 DEADLOCKS: A SAFE, LOUD CRASH
================================================================================

  ch := make(chan int)
  ch <- 42   // nobody will ever receive this

  fatal error: all goroutines are asleep - deadlock!

  This is NOT an infinite hang - Go's runtime detects that every
  goroutine is permanently stuck and crashes the whole program
  immediately. A deadlock in Go is safe to trigger and learn from.

================================================================================
                    THE WORKER POOL PATTERN
================================================================================

A fixed number of worker goroutines pull jobs from a shared `jobs`
channel and push results onto a shared `results` channel:

  for w := 1; w <= numWorkers; w++ {
      go worker(w, jobs, results, &wg)
  }
  for j := range allJobs { jobs <- j }
  close(jobs)      // lets each worker's range loop end
  wg.Wait()
  close(results)   // safe now - every worker is confirmed done

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. CHANNELS
   Typed conduits between goroutines - share memory BY communicating.

2. UNBUFFERED VS BUFFERED
   Unbuffered rendezvous; buffered only blocks once full.

3. CLOSING
   close(ch) means "no more sends, ever." comma-ok / range detect it.

4. DIRECTION TYPES
   chan<- (send-only), <-chan (receive-only) - compiler-enforced.

5. FAILURE MODES
   Deadlock = fatal error, immediate crash. Send/close on closed
   channel = panic. Both are loud and safe, not silent or hanging.

6. PATTERNS
   Worker pools bound concurrency; pipelines chain stages via channels.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Deadlocking on an unbuffered send
  ch := make(chan int)
  ch <- 1   // nothing will ever receive - fatal error: deadlock!

✅ RIGHT
  ch := make(chan int)
  go func() { fmt.Println(<-ch) }()
  ch <- 1

---

❌ WRONG: Sending on a closed channel
  close(ch)
  ch <- 1   // panic: send on closed channel

✅ RIGHT: Only the sender closes, only once truly done sending

---

❌ WRONG: Closing a channel twice
  close(ch)
  close(ch)   // panic: close of closed channel

✅ RIGHT: Close exactly once, from exactly one place

---

❌ WRONG: Forgetting to close before a range loop needs it
  func produce(ch chan<- int) {
      for i := 0; i < 5; i++ { ch <- i }
      // missing: close(ch) - the consumer's range loop hangs forever
  }

✅ RIGHT: defer close(ch) in the producer

================================================================================
                      QUICK FAQ
================================================================================

Q: Why use a channel instead of a mutex-protected variable?
A: A mutex protects a variable that stays shared. A channel hands off
   ownership of a value entirely - once sent, the sender is done with it.
   Use a mutex for pure shared-state protection, a channel for handoff
   or signaling.

Q: Does a Go deadlock hang my program forever?
A: No - Go detects it and crashes immediately with
   "fatal error: all goroutines are asleep - deadlock!" It's a fast,
   safe failure, not an infinite hang.

Q: What's the difference between the two "closed channel" panics?
A: "send on closed channel" happens when you send after closing.
   "close of closed channel" happens when you close the same channel
   twice. Both mean: closing already happened; that state is final.

Q: Why would anyone want a channel that blocks forever (nil channel)?
A: On its own, it's not useful - but inside a select statement
   (Level 22), a nil channel's case is simply never chosen, which is
   how you disable one branch of a select at runtime.

Q: Who should close a channel?
A: Always the sender, and only once it's truly done sending. Never
   close from the receiving side.
