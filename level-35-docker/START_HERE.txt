                    IMPORTANT: A DIFFERENT KIND OF LEVEL
================================================================================

Every level before this one (0-34) runs 100% through the Go toolchain alone -
go run, go build, go test. Docker is a SEPARATE tool from a separate vendor,
with its own daemon that has to be installed and running on your machine.

In the environment that authored this course, the Docker daemon was NOT
reachable (checked with `docker version` / `docker info` - the client was
present but could not connect to a running daemon). Because of this:

  - The Go source code in this level WAS genuinely compiled and run with
    go build / go run, and its output IS real and verified, same as every
    other level.
  - The Dockerfile and docker-compose.yml content IS written correctly per
    Docker's documented behavior.
  - The docker build / docker run / docker compose OUTPUT shown in this
    level's files is ILLUSTRATIVE ONLY - it was not actually captured from
    a real build. Every such block is clearly labeled.

When you run these commands yourself with Docker installed, trust YOUR OWN
real output over any numbers or exact log text shown in this course.

You will need Docker Desktop (or an equivalent Docker Engine) installed and
running to actually complete the docker build / docker run / docker compose
steps in the exercises.

================================================================================
                      THE BIG PICTURE
================================================================================

What is a Container?
  → A package that bundles your program with a minimal, precisely-specified
    slice of an operating system, so it runs identically everywhere
  → Lighter than a virtual machine - shares the host's kernel, isolates
    only the process, filesystem, and network

Why Go Fits This Unusually Well:
  → go build produces ONE statically-linked binary - no interpreter, no
    VM, no runtime to install alongside it (unlike Python, Node, or Java)
  → This means a Go container's runtime stage can be nearly empty: just
    the binary, nothing else

================================================================================
                 A FIRST SIMPLE DOCKERFILE
================================================================================

  FROM golang:1.23
  WORKDIR /app
  COPY . .
  RUN go build -o server .
  EXPOSE 8080
  CMD ["./server"]

This works, but ships the ENTIRE golang toolchain image to production.
Multi-stage builds (next) fix that.

================================================================================
                 MULTI-STAGE BUILDS
================================================================================

  # ---- build ----
  FROM golang:1.23 AS builder
  WORKDIR /app
  COPY go.mod go.sum ./
  RUN go mod download
  COPY . .
  RUN CGO_ENABLED=0 go build -o server .

  # ---- runtime ----
  FROM alpine:3.20
  COPY --from=builder /app/server /server
  CMD ["/server"]

The build stage has the compiler and source code. The runtime stage starts
FRESH and copies in only the compiled binary - no toolchain, no source,
dramatically smaller image.

================================================================================
                 .dockerignore
================================================================================

Excludes files from ever reaching the build context - before ANY COPY runs:

  .git
  .env
  *.md
  .vscode/

Never let .git or .env reach a build context. Secrets baked into an image
layer can be extracted even if a later instruction appears to remove them.

================================================================================
                 LAYER CACHING ORDER
================================================================================

  COPY go.mod go.sum ./     <- only invalidated when DEPENDENCIES change
  RUN go mod download       <- cached across ordinary source edits!
  COPY . .                  <- invalidated by source changes (expected)
  RUN go build -o server .

Rule: least-frequently-changing instructions first, most-frequently-
changing instructions last.

================================================================================
                 ENVIRONMENT VARIABLES = LEVEL 34, LIVE
================================================================================

  ENV PORT=8080                          (Dockerfile default)
  docker run -e PORT=9090 myimage        (runtime override, no rebuild)

Same image, different behavior per environment - exactly the configuration
pattern Level 34 teaches, now driven by Docker (and later, Kubernetes in
Level 36) instead of a local .env file.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Skipping multi-stage builds
  FROM golang:1.23 ... CMD ["./server"]   // ships the whole toolchain

✅ RIGHT: Multi-stage, copy only the compiled binary into a minimal base

---

❌ WRONG: No .dockerignore
  COPY . .   // .git, .env, editor clutter all sent to the daemon

✅ RIGHT: Write .dockerignore BEFORE your first COPY . .

---

❌ WRONG: Hardcoding secrets
  ENV DATABASE_PASSWORD=hunter2   // baked into the image permanently

✅ RIGHT: docker run -e DATABASE_PASSWORD=... at runtime

---

❌ WRONG: Unpinned tags
  FROM golang:latest   // unreproducible - moves out from under you

✅ RIGHT: FROM golang:1.23-alpine (exact, reproducible)

================================================================================
                      QUICK FAQ
================================================================================

Q: Why does this level need a real tool install, when no other level did?
A: Docker is a separate piece of software with its own daemon - not part of
   the Go toolchain like `go get` dependencies (Gin in Level 28, a SQL
   driver in Level 29). You need Docker Desktop (or equivalent) installed
   and running.

Q: Why is a multi-stage build so much smaller?
A: The build stage needs the compiler and source; the runtime stage only
   needs to RUN the already-compiled binary, so it can start from a nearly
   empty base and skip the toolchain and source entirely.

Q: Why copy go.mod before the rest of the source?
A: Docker caches each instruction as a layer. Dependency downloads only
   need to re-run when go.mod/go.sum change - not on every source edit.

Q: How does this connect to Level 34?
A: Level 34 teaches reading config from environment variables. This level
   is what actually SETS those variables for a deployed container - ENV
   for defaults, docker run -e to override per environment.
