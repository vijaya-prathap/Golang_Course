Welcome to Level 25! You've mastered Context (Level 24). Now it's time to
learn GENERICS - how to write ONE function or type that works safely across
MANY types, without giving up the compiler's type checking.

Before generics, you had two bad options: write the same function once per
type (SumInts, SumFloats, ...), or write it once using `any` and lose type
safety (runtime panics from type assertions instead of compile errors).
Generics give you a third option - one implementation, full safety.

================================================================================
                      THE BIG PICTURE
================================================================================

What Are Generics?
  → A way to write a function or type once, using a placeholder ("type
    parameter") for a type that's filled in at each call site
  → The compiler checks every call and generates correct, type-safe code
    for each concrete type you use

Why Generics Matter:
  → Before Go 1.18, "works with any type" meant either copy-pasting the same
    function per type, or using `any` and losing compile-time safety
  → Generics let you write it once AND keep the compiler's help

================================================================================
                 BEFORE / AFTER: THE CORE MOTIVATION
================================================================================

BEFORE (duplication):

  func SumInts(nums []int) int { ... }
  func SumFloats(nums []float64) float64 { ... }

BEFORE (any - loses type safety):

  func SumAny(nums []any) any {
      var total int
      for _, n := range nums {
          total += n.(int)   // panics at runtime if the slice isn't all ints
      }
      return total
  }

AFTER (generics - one function, fully type-safe):

  type Number interface {
      int | int64 | float64
  }

  func Sum[T Number](nums []T) T {
      var total T
      for _, n := range nums {
          total += n
      }
      return total
  }

  Sum([]int{1, 2, 3})         // works, T = int
  Sum([]float64{1.5, 2.5})    // works, T = float64
  Sum([]string{"a", "b"})     // does NOT compile - string isn't a Number

================================================================================
                 TYPE PARAMETER SYNTAX
================================================================================

  func Map[T, U any](s []T, f func(T) U) []U { ... }

  Calling with inference (most common):
    Map(nums, func(n int) string { return fmt.Sprintf("%d", n) })

  Calling with explicit type arguments (always valid):
    Map[int, string](nums, func(n int) string { return fmt.Sprintf("%d", n) })

================================================================================
                 CONSTRAINTS: any, comparable, CUSTOM
================================================================================

  any          → accepts anything, but you can't do much without a type
                 assertion first

  comparable   → any type supporting == and != - required for == inside a
                 generic function, or to use the type parameter as a map key

  custom       → your own interface with a type set, defined LOCALLY, no
                 external packages needed:

                 type Number interface {
                     int | int64 | float64
                 }

================================================================================
                 GENERIC TYPES: Stack[T] AND Pair[K, V]
================================================================================

  type Stack[T any] struct {
      items []T
  }

  func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
  func (s *Stack[T]) Pop() (T, bool) { ... }

  type Pair[K, V any] struct {
      Key   K
      Value V
  }

Every method on a generic type must repeat its type parameter:
func (s *Stack[T]) Push(...) - not func (s *Stack) Push(...).

================================================================================
                 TYPE INFERENCE: WHEN IT FAILS
================================================================================

Go infers type arguments from the REGULAR ARGUMENTS you pass - never from
the return type alone.

  func Zero[T any]() T { var z T; return z }

  zero := Zero()        // ❌ does NOT compile - nothing to infer T from
  zero := Zero[int]()   // ✅ must specify explicitly

Real compiler error (captured during authoring):
  in call to Zero, cannot infer T (declared at ./main.go:5:11)

================================================================================
                 WHEN NOT TO USE GENERICS
================================================================================

Generics are for the SAME algorithm/structure over arbitrary ELEMENT types.
They are NOT a replacement for small interfaces (Level 15) when what varies
is BEHAVIOR, not the stored type.

  // ✅ A plain interface already expresses "things that have an area"
  type Shape interface {
      Area() float64
  }
  func TotalArea(shapes []Shape) float64 { ... }   // mixes Circle + Rectangle

  // ❌ Overkill - only works with ONE concrete shape type per call
  func TotalArea[T Shape](shapes []T) float64 { ... }

Don't generic-ize "just in case." Start concrete, add a type parameter only
when you genuinely need a second type.

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. THE PROBLEM
   Duplication (one func per type) vs. any (loses type safety) - generics
   give you neither downside.

2. SYNTAX
   func Name[T Constraint](params) ReturnType - type parameters in [...].

3. CONSTRAINTS
   any (anything) -> comparable (==, map keys) -> custom type-set interface
   (arithmetic, custom operators).

4. GENERIC TYPES
   Struct types can carry type parameters too; methods must repeat them.

5. INFERENCE
   Works when a type parameter appears in a regular argument. Fails when it
   appears only in the return type - specify explicitly then.

6. JUDGMENT
   Generics for arbitrary element types. Small interfaces (Level 15) for
   arbitrary behavior. Don't force one to do the other's job.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Forgetting comparable and using == anyway
  func Contains[T any](s []T, v T) bool {
      for _, item := range s {
          if item == v { return true }   // any doesn't guarantee ==
      }
      return false
  }
  Real error: invalid operation: item == v (incomparable types in type set)

✅ RIGHT
  func Contains[T comparable](s []T, v T) bool { ... }

---

❌ WRONG: Overusing generics where a plain interface would be simpler
  func TotalArea[T Shape](shapes []T) float64 { ... }

✅ RIGHT
  func TotalArea(shapes []Shape) float64 { ... }

---

❌ WRONG: Passing a type outside a custom constraint's type set
  Sum([]string{"a", "b"})   // Number is int | int64 | float64
  Real error: string does not satisfy Number (string missing in int | int64 | float64)

---

❌ WRONG: Expecting inference when T only appears in the return type
  zero := Zero()   // cannot infer T
  Real error: in call to Zero, cannot infer T (declared at ./main.go:5:11)

✅ RIGHT: zero := Zero[int]()

================================================================================
                      QUICK FAQ
================================================================================

Q: Is any the same as interface{}?
A: Yes - any is a built-in alias for the empty interface, introduced
   alongside generics in Go 1.18.

Q: Why can't I use == inside a generic function constrained with any?
A: any doesn't guarantee == is defined. Use comparable instead.

Q: Do custom constraints need an external package?
A: No - type Number interface { int | int64 | float64 } is just a regular
   interface with a type set, defined entirely in your own code.

Q: When should I use a generic type parameter instead of an interface?
A: When the same algorithm/structure needs to work over arbitrary element
   types that don't need to "do" anything (a stack, a cache, Sum). Use an
   interface (Level 15) when concrete types need to behave differently.

Q: Why does Go sometimes require explicit type arguments?
A: Inference only looks at regular arguments. If a type parameter appears
   only in the return type, there's nothing to infer it from.
