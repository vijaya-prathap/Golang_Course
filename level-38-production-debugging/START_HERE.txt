================================================================================
                      THE BIG PICTURE
================================================================================

What Makes Production Debugging Different?
  → No debugger attached from the start - the process was already
    running before anything went wrong
  → Often can't reproduce the bug locally - it depends on real load,
    real data, real network conditions
  → Evidence has to be captured IN THE MOMENT - logs, metrics, and
    profiles pulled from the live process, not guessed at afterward

Go's Answer:
  → net/http/pprof exposes CPU, memory, and goroutine profiles over
    plain HTTP - pull them from a running process without stopping it
  → runtime.NumGoroutine() / ReadMemStats() give cheap, constant,
    in-process numbers with no separate tooling
  → Delve (dlv) can ATTACH to an already-running process - no restart
  → A real health check and correlation-ID logging turn "something's
    wrong" into "here's exactly what, where, and since when"

================================================================================
                   THE pprof ENDPOINTS AT A GLANCE
================================================================================

  import _ "net/http/pprof"   // side-effect import

  /debug/pprof/profile?seconds=30    CPU profile (blocks for 30s)
  /debug/pprof/heap?gc=1             live heap snapshot
  /debug/pprof/goroutine?debug=2     full goroutine stack dump

  ⚠️ GOTCHA: this only registers on http.DefaultServeMux. A custom
  http.NewServeMux() gets NONE of these endpoints unless you register
  pprof.Index/Profile/Symbol/Trace/Cmdline on it yourself. This was
  reproduced for real while writing this level - a plain 404, no
  warning, no hint that pprof was ever imported.

================================================================================
                 READING A CPU PROFILE (REAL EXAMPLE)
================================================================================

  go tool pprof -top -nodecount=10 ./server cpu.pprof

  Real captured output from this level's own verification:

        flat  flat%   sum%        cum   cum%
       9.42s 59.47% 59.47%      9.42s 59.47%  syscall.rawsyscalln
       5.57s 35.16% 94.63%      5.72s 36.11%  main.isPrime (inline)
       0.29s  1.83% 96.46%      6.03s 38.07%  main.countPrimesHandler

  main.isPrime - the function actually doing the CPU-bound work - is
  unambiguously the hottest USER code frame. Reading flat% top-down is
  the whole skill.

================================================================================
                 A REAL DEADLOCK (NOT A HYPOTHETICAL)
================================================================================

  ch := make(chan int)
  <-ch   // nobody will ever send - deadlock

  fatal error: all goroutines are asleep - deadlock!

  goroutine 1 [chan receive]:
  main.main()
          .../main.go:5 +0x30
  exit status 2

  A deadlock CRASHES immediately and loudly - it does not hang
  silently. Go's own runtime detector already printed the evidence
  for you.

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. WHY IT'S DIFFERENT
   No pre-attached debugger, often no local repro, evidence must be
   captured live.

2. PROFILING
   CPU (/debug/pprof/profile), memory (/debug/pprof/heap), goroutines
   (/debug/pprof/goroutine) - all real HTTP endpoints.

3. LIGHTWEIGHT DIAGNOSTICS
   runtime.NumGoroutine() and runtime.ReadMemStats() - cheap, constant,
   in-process.

4. ISSUE SIGNATURES
   Leaks: numbers rise and never fall. Deadlocks: the whole process
   crashes immediately with a specific fatal error.

5. DELVE
   dlv exec (fresh process) and dlv attach <pid> (already-running
   process) - a real debugger, not just print statements.

6. HEALTH & LOGGING
   /healthz reports REAL dependency state. Correlation IDs let you
   trace one request across every log line it produces.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Exposing /debug/pprof/ on a public listener
✅ RIGHT: Bind to 127.0.0.1, or gate behind auth/internal-only network

---

❌ WRONG: Building a custom http.NewServeMux() and expecting pprof to
          just work on it
✅ RIGHT: Use http.DefaultServeMux, or register pprof's handlers
          explicitly on your own mux

---

❌ WRONG: Capturing a CPU profile while the server is idle
✅ RIGHT: Profile WHILE real (or simulated) load is hitting the service

---

❌ WRONG: A /healthz that always returns 200 OK
✅ RIGHT: Check real dependencies (DB, goroutine count) and return 503
          when something is actually wrong

---

❌ WRONG: Log lines during an incident with no shared identifier
✅ RIGHT: A correlation ID (request_id) on every log line for a request,
          assigned once at the boundary

================================================================================
                      QUICK FAQ
================================================================================

Q: Do I need a real production server to do this level?
A: No - every exercise runs a real local Go program that profiles or
   diagnoses itself. The techniques transfer directly to a real
   deployed service.

Q: Why aren't any /debug/pprof/ endpoints responding for me?
A: You probably built a custom http.NewServeMux() - net/http/pprof's
   side-effect import only registers on http.DefaultServeMux.

Q: Is it safe to leave pprof enabled in production?
A: Only if it's not reachable publicly - bind to loopback or gate
   behind auth. Exposed publicly, it's a real security issue.

Q: What if dlv isn't installed on my machine?
A: Install it from https://github.com/go-delve/delve, or read Section 7
   and Exercise 8 as reference - dlv (v1.27.0) WAS available while
   writing this level, so that content is real, captured output.

Q: How is a goroutine leak different from a deadlock?
A: A deadlock means EVERY goroutine is blocked - the runtime detects
   this and crashes immediately. A leak means SOME goroutines are stuck
   while the rest of the program runs fine - it doesn't crash, it just
   slowly accumulates dead weight.
