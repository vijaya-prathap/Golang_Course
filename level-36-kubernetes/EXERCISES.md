# Level 36: Kubernetes - Exercises

> ⚠️ **This level's Kubernetes manifests could not be applied to or tested against a real cluster** in the environment that authored this course, because no cluster (and possibly no `kubectl`) is available here. The `kubectl` CLI binary was present, but even `kubectl apply --dry-run=client` requires reaching a live API server (or a cached OpenAPI schema) for discovery in this environment, so client-side dry-run validation was not possible either. As a fallback, every manifest below was passed through a plain YAML parser to confirm it is syntactically well-formed - **that is not the same as Kubernetes schema validation.** Every manifest is written correctly per the current stable Kubernetes API, but - unlike every Go-code level in this course - none of it was verified against a live, running cluster. When you run these yourself with a cluster (even a local `kind` or `minikube` one), trust your own real output over anything shown here.

Complete all exercises in order. Each exercise builds on previous knowledge. All examples build toward one running example application, `books-api` (the same "books" REST resource from Level 27), using the image `books-api:1.0.0` from Level 35.

## Exercise 1: A Basic Pod Manifest

**Objective:** Write and understand the smallest possible real-world Pod manifest

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise1
cd ~/k8s/level36-exercise1
```

2. Create `pod.yaml`:

```bash
cat > pod.yaml << 'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: books-api-pod
  labels:
    app: books-api
spec:
  containers:
    - name: books-api
      image: books-api:1.0.0
      ports:
        - containerPort: 8080
EOF
```

3. Apply it against your own cluster:

```bash
kubectl apply -f pod.yaml
kubectl get pod books-api-pod
```

**Illustrative Output (unverified against a live cluster):**

```

```

```
NAME            READY   STATUS    RESTARTS   AGE
books-api-pod   1/1     Running   0          5s
```

**Learning Objectives:**
- ✅ Write a minimal, valid Pod manifest
- ✅ Identify `apiVersion`, `kind`, `metadata`, and `spec` in a real manifest
- ✅ Understand that `containerPort` documents the port the container listens on

## Exercise 2: A Deployment With 3 Replicas

**Objective:** Manage a set of identical Pods instead of one bare Pod

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise2
cd ~/k8s/level36-exercise2
```

2. Create `deployment.yaml`:

```bash

apiVersion: apps/v1
kind: Deployment
metadata:
  name: books-api
  labels:
    app: books-api
spec:
  replicas: 3
```

## Exercise 3: A ClusterIP Service

**Objective:** Give the Deployment's Pods one stable, internal address

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise3
cd ~/k8s/level36-exercise3
```

2. Create `service-clusterip.yaml`:

```bash
cat > service-clusterip.yaml << 'EOF'
apiVersion: v1
kind: Service
metadata:
  name: books-api
spec:
  type: ClusterIP
  selector:
    app: books-api
  ports:
    - port: 80
      targetPort: 8080
      protocol: TCP
EOF
```

3. Apply it and inspect it:

```bash
kubectl apply -f service-clusterip.yaml
kubectl get service books-api
```

**Illustrative Output (unverified against a live cluster):**

```
service/books-api created
```

```
NAME        TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
books-api   ClusterIP   10.96.142.7    <none>        80/TCP    5s
```

Any other Pod in the cluster can now reach the books-api Pods at `http://books-api/` (port 80) or `http://books-api.default.svc.cluster.local/` by its full DNS name - regardless of which specific Pods are currently running.

**Learning Objectives:**
- ✅ Write a ClusterIP Service manifest
- ✅ Understand `port` (what the Service exposes) vs `targetPort` (what the container listens on)
- ✅ Understand ClusterIP is internal-only (the default Service type)

## Exercise 4: A NodePort Service Variant

**Objective:** Compare NodePort to ClusterIP for simple external access

**Instructions:**

3. Apply it and inspect it:


**Illustrative Output (unverified against a live cluster):**

Unlike the ClusterIP Service, this one is reachable from outside the cluster at `<any-node-ip>:30080` - useful for local development against `kind`/`minikube` or quick demos, but a `LoadBalancer` Service (or an Ingress, see Bonus Challenge 2) is the normal choice for production external traffic on a cloud provider.

- ✅ Compare NodePort against ClusterIP for reachability

## Exercise 5: A ConfigMap and a Pod That Uses It

**Objective:** Externalize non-sensitive configuration instead of hardcoding it

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise5
cd ~/k8s/level36-exercise5
```

2. Create `configmap.yaml`:

```bash
cat > configmap.yaml << 'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: books-api-config
data:
  LOG_LEVEL: "info"
  MAX_BOOKS_PER_PAGE: "20"
EOF
```

3. Create `pod-with-configmap.yaml`, a Pod that consumes both keys as environment variables:

```bash
cat > pod-with-configmap.yaml << 'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: books-api-config-demo
  labels:
    app: books-api
spec:
  containers:
    - name: books-api
      image: books-api:1.0.0
      ports:
        - containerPort: 8080
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: books-api-config
              key: LOG_LEVEL
        - name: MAX_BOOKS_PER_PAGE
          valueFrom:
            configMapKeyRef:
              name: books-api-config
              key: MAX_BOOKS_PER_PAGE
EOF
```

4. Apply both and confirm the values landed inside the container:

```bash
kubectl apply -f configmap.yaml
kubectl apply -f pod-with-configmap.yaml
kubectl exec books-api-config-demo -- printenv LOG_LEVEL
```

**Illustrative Output (unverified against a live cluster):**

```
configmap/books-api-config created
pod/books-api-config-demo created
```

```
info
```

**Learning Objectives:**
- ✅ Write a ConfigMap with multiple key/value pairs
- ✅ Reference individual ConfigMap keys as Pod environment variables with `configMapKeyRef`
- ✅ Understand the Go program reads these the same way as any env var (`os.Getenv`, from Level 34)

## Exercise 6: A Secret and a Pod That Uses It

**Objective:** Externalize sensitive configuration using a Secret instead of a ConfigMap

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise6
cd ~/k8s/level36-exercise6
```

2. Create `secret.yaml`:

```bash
cat > secret.yaml << 'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: books-api-secret
type: Opaque
stringData:
  DB_PASSWORD: "s3cr3t-value"
EOF
```

3. Create `pod-with-secret.yaml`:

```bash
cat > pod-with-secret.yaml << 'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: books-api-secret-demo
  labels:
    app: books-api
spec:
  containers:
    - name: books-api
      image: books-api:1.0.0
      ports:
        - containerPort: 8080
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: books-api-secret
              key: DB_PASSWORD
EOF
```

4. Apply both, then inspect the Secret's stored (base64) form:

```bash
kubectl apply -f secret.yaml
kubectl apply -f pod-with-secret.yaml
kubectl get secret books-api-secret -o jsonpath='{.data.DB_PASSWORD}'
```

**Illustrative Output (unverified against a live cluster):**

```
secret/books-api-secret created
pod/books-api-secret-demo created
```

```
czNjcjN0LXZhbHVl
```

That is `s3cr3t-value` base64-encoded - proof that `stringData` values get stored as base64 `data` internally, and a reminder that base64 is an encoding, not encryption.

**Learning Objectives:**
- ✅ Write a Secret manifest using `stringData` for readable plain-text input
- ✅ Reference a Secret key as a Pod environment variable with `secretKeyRef`
- ✅ Understand Secrets are base64-encoded at rest, not encrypted, by default

## Exercise 7: Adding Readiness and Liveness Probes

**Objective:** Make the Deployment self-report health, bridging Level 27's HTTP servers

**Instructions:**

1. Create a working directory:

```bash
mkdir -p ~/k8s/level36-exercise7
cd ~/k8s/level36-exercise7
```

2. Create `deployment-with-probes.yaml` - the Exercise 2 Deployment, with a `/ready` readiness probe and a `/healthz` liveness probe added (both assumed to be handlers added to the `books-api` Go server from Level 27):

```bash
cat > deployment-with-probes.yaml << 'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: books-api
  labels:
    app: books-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: books-api
  template:
    metadata:
      labels:
        app: books-api
    spec:
      containers:
        - name: books-api
          image: books-api:1.0.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 20
EOF
```

3. Apply it and watch Pod readiness:

```bash
kubectl apply -f deployment-with-probes.yaml
kubectl get pods -l app=books-api -w
```

**Illustrative Output (unverified against a live cluster):**

```
deployment.apps/books-api configured
```

```
NAME                         READY   STATUS    RESTARTS   AGE
books-api-6c9d7f4b8c-a1b2c   0/1     Running   0          2s
books-api-6c9d7f4b8c-a1b2c   1/1     Running   0          6s
```

Note the `READY` column moving from `0/1` to `1/1` a few seconds after the Pod starts `Running` - that gap is exactly `initialDelaySeconds` plus however long the first successful readiness check takes.

**Learning Objectives:**
- ✅ Add both a readiness and a liveness probe to a Deployment's Pod template
- ✅ Understand `httpGet.path`/`httpGet.port`, `initialDelaySeconds`, and `periodSeconds`
- ✅ Explain why a Pod can show `Running` but not yet `READY`

## Bonus Challenges

### Challenge 1: HorizontalPodAutoscaler

Write a `HorizontalPodAutoscaler` that automatically scales the `books-api` Deployment between 2 and 10 replicas, targeting 70% average CPU utilization.

```bash
mkdir -p ~/k8s/level36-bonus1
cd ~/k8s/level36-bonus1
```

**Hints:**
- `apiVersion: autoscaling/v2`, `kind: HorizontalPodAutoscaler`
- `spec.scaleTargetRef` points at the Deployment by `apiVersion`, `kind`, and `name`
- `spec.minReplicas` / `spec.maxReplicas` set the bounds
- `spec.metrics` is a list; use a `type: Resource` entry with `resource.name: cpu` and `resource.target.type: Utilization` / `resource.target.averageUtilization: 70`
- An HPA only works if the target Deployment's containers have `resources.requests.cpu` set (Exercise 8) - utilization is measured relative to the request

### Challenge 2: Ingress for External Routing

Write an `Ingress` that routes external HTTP traffic for the host `books.example.com` to the `books-api` ClusterIP Service on port 80.

```bash
mkdir -p ~/k8s/level36-bonus2
cd ~/k8s/level36-bonus2
```

**Hints:**
- `apiVersion: networking.k8s.io/v1`, `kind: Ingress`
- `spec.rules[].host` is the external hostname; `spec.rules[].http.paths[]` lists path-based routes
- Each path needs a `pathType` (`Prefix` is the common default) and a `backend.service.name` / `backend.service.port.number` pointing at the Service
- An Ingress needs an Ingress *controller* (e.g. nginx-ingress) actually running in the cluster to do anything - the Ingress object alone is just a routing rule

### Challenge 3: Rolling Update Strategy Configuration

Add an explicit `strategy` block to the `books-api` Deployment that allows one extra Pod above the desired replica count during a rollout, but never allows the available count to drop below the full desired count.

```bash
mkdir -p ~/k8s/level36-bonus3
cd ~/k8s/level36-bonus3
```

**Hints:**
- `spec.strategy.type: RollingUpdate` (also the default if omitted)
- `spec.strategy.rollingUpdate.maxSurge` - how many Pods above `replicas` are allowed during the rollout (e.g. `1`)
- `spec.strategy.rollingUpdate.maxUnavailable` - how many of the desired Pods are allowed to be unavailable during the rollout (`0` means never drop below full capacity)
- `maxSurge: 1` with `maxUnavailable: 0` is a common "zero-downtime, one extra Pod at a time" configuration
