================================================================================
                      THE BIG PICTURE
================================================================================

What is Kubernetes?
  → A system that runs your containers across a cluster of machines,
    restarting them when they crash, scaling them up/down, rolling out
    updates without downtime, and load-balancing traffic across replicas
  → You describe DESIRED STATE in YAML; Kubernetes continuously works to
    make reality match it

Why Kubernetes Matters:
  → docker-compose (Level 35) is enough for one machine you watch by hand
  → Real production systems span many machines, need automatic healing,
    need to scale under load, and need zero-downtime deployments -
    Kubernetes is the standard answer to all four at once

================================================================================
                 THE THREE CORE OBJECTS
================================================================================

1. POD - the smallest deployable unit (one or more containers)

  apiVersion: v1
  kind: Pod
  metadata:
    name: books-api-pod
  spec:
    containers:
      - name: books-api
        image: books-api:1.0.0
        ports:
          - containerPort: 8080

2. DEPLOYMENT - manages N identical Pod replicas, self-heals, handles rollouts

  apiVersion: apps/v1
  kind: Deployment
  spec:
    replicas: 3
    selector: { matchLabels: { app: books-api } }
    template:
      metadata: { labels: { app: books-api } }
      spec:
        containers:
          - name: books-api
            image: books-api:1.0.0

3. SERVICE - a stable network endpoint load-balancing across matching Pods

  apiVersion: v1
  kind: Service
  spec:
    type: ClusterIP
    selector: { app: books-api }
    ports:
      - port: 80
        targetPort: 8080

================================================================================
                 CONFIGMAPS AND SECRETS
================================================================================

Externalize configuration instead of baking it into the image (bridges
Level 34):

  ConfigMap  →  non-sensitive values (LOG_LEVEL, feature flags, ...)
  Secret     →  sensitive values (passwords, API keys, ...) - base64 at
                rest, NOT encrypted by default

Both get injected into a Pod as environment variables via
configMapKeyRef / secretKeyRef, and the Go program reads them with the
same os.Getenv() calls from Level 34 - it never knows where the value
came from.

================================================================================
                 READINESS AND LIVENESS PROBES
================================================================================

  readinessProbe  → "Can this Pod take traffic right now?"
                     fails → removed from the Service, NOT restarted
  livenessProbe   → "Is this Pod still alive?"
                     fails → container killed and restarted

  readinessProbe:
    httpGet: { path: /ready, port: 8080 }
    initialDelaySeconds: 5
    periodSeconds: 10

This bridges Level 27 - your Go HTTP server needs a real health endpoint
for Kubernetes to check.

================================================================================
                 RESOURCE REQUESTS AND LIMITS
================================================================================

  requests → guaranteed minimum; used by the scheduler to place the Pod
  limits   → hard cap; CPU is throttled, memory gets the Pod OOMKilled

  resources:
    requests: { cpu: "100m", memory: "64Mi" }
    limits:   { cpu: "500m", memory: "256Mi" }

Always set both - an unlimited Pod can starve every other Pod on its node.

================================================================================
                    kubectl BASICS
================================================================================

  kubectl apply -f app.yaml     → create/update (DECLARATIVE, safe to re-run)
  kubectl get pods              → list objects
  kubectl describe pod <name>   → full detail + events (debug here first)
  kubectl logs <pod>            → container stdout/stderr
  kubectl delete -f app.yaml    → remove everything in the file

apply is declarative: it makes the cluster match the file, every time you
run it - it is NOT a one-off imperative action like `kubectl create`.

================================================================================
                    ROLLING UPDATES AND ROLLBACKS
================================================================================

Changing a Deployment's image and re-applying it replaces Pods gradually,
never dropping below full serving capacity (as long as probes are set up
correctly):

  kubectl set image deployment/books-api books-api=books-api:1.1.0
  kubectl rollout status deployment/books-api
  kubectl rollout undo deployment/books-api      ← revert if it goes wrong

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. CORE OBJECTS
   Pod (containers) → Deployment (N replicas, self-heals) → Service (stable address)

2. CONFIGURATION
   ConfigMap (non-sensitive) / Secret (sensitive) → injected as env vars

3. HEALTH
   readinessProbe (traffic-ready?) / livenessProbe (still alive?)

4. RESOURCES
   requests (guaranteed, scheduling) / limits (hard cap, stability)

5. OPERATIONS
   kubectl apply is declarative; rollouts replace Pods gradually;
   kubectl rollout undo reverts a bad release

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: No resource limits
  resources: {}   // one leaking Pod can starve its whole node

✅ RIGHT: Always set requests AND limits

---

❌ WRONG: Missing readiness probe
  containers: [{ name: books-api, image: books-api:1.0.0 }]
  // traffic hits the Pod before it's actually ready

✅ RIGHT: Add a readinessProbe backed by a real health endpoint

---

❌ WRONG: Hardcoding config that should be externalized
  env: [{ name: LOG_LEVEL, value: "info" }]

✅ RIGHT: Reference a ConfigMap/Secret key instead

---

❌ WRONG: Treating kubectl apply as a one-off imperative command
  (confusing it with kubectl create, which fails on re-run)

✅ RIGHT: apply is declarative and safe to run repeatedly

================================================================================
                      QUICK FAQ
================================================================================

Q: Do I need a real cluster to do this level?
A: To truly verify anything, yes - a free local cluster (kind or minikube)
   is enough. This course's authoring environment didn't have one, which
   is why exercise outputs are labeled illustrative rather than verified.

Q: Why use a Deployment instead of a bare Pod?
A: A bare Pod that crashes stays dead. A Deployment supervises its Pods
   and replaces any that disappear, plus gives you scaling and rollouts.

Q: ClusterIP vs NodePort vs LoadBalancer - which do I use?
A: ClusterIP for internal traffic (the default). NodePort for simple
   local/demo external access. LoadBalancer for real production external
   access on a cloud platform.

Q: Are Secrets actually secure?
A: Not by themselves - they're base64-encoded, not encrypted, by default.
   Real protection comes from cluster RBAC, encryption-at-rest, and never
   committing real secret values to files you check into version control.

Q: What's the difference between kubectl apply and kubectl create?
A: apply is declarative and safe to re-run; create is a one-off imperative
   action that fails if the object already exists.
