================================================================================
                      THE BIG PICTURE
================================================================================

What Is an Error, Really?
  → Just a value: anything with an Error() string method
  → No exceptions, no throw, no hidden control flow
  → A function that can fail SAYS SO in its signature: (Result, error)

Why Errors Matter:
  → Every real program deals with things that can go wrong: bad input,
    missing files, network failures, invalid data
  → Go makes failure visible right where it happens, instead of hiding
    it behind a distant catch block

================================================================================
                    THE error INTERFACE
================================================================================

  type error interface {
      Error() string
  }

  That's the WHOLE interface. Any type with that one method IS an error -
  implicitly, exactly like every interface from Level 15.

================================================================================
                 THE FUNDAMENTAL PATTERN
================================================================================

  result, err := divide(10, 2)
  if err != nil {
      fmt.Println("Error:", err)
      return
  }
  fmt.Println("10 / 2 =", result)

  nil means success. Non-nil means "something went wrong."

================================================================================
                 CREATING ERRORS
================================================================================

  errors.New("division by zero")           // fixed message
  fmt.Errorf("user %d not found", id)       // formatted message
  fmt.Errorf("loading config: %w", err)     // WRAPPED - keeps err traceable

  Message style: lowercase, no trailing period, include relevant values.

================================================================================
                 WRAPPING AND UNWRAPPING
================================================================================

  base := errors.New("connection refused")
  wrapped := fmt.Errorf("dialing database: %w", base)
  top := fmt.Errorf("starting server: %w", wrapped)

  fmt.Println(top)
  // starting server: dialing database: connection refused

  errors.Unwrap(top)      // -> wrapped
  errors.Unwrap(wrapped)  // -> base
  errors.Unwrap(base)     // -> nil

  KEY GOTCHA - %v copies the TEXT but NOT the chain:
  fmt.Errorf("dialing database: %v", base)  // errors.Unwrap gives nil!

================================================================================
                 errors.Is AND errors.As
================================================================================

  errors.Is(err, target)   -> "is target ANYWHERE in err's chain?"
  errors.As(err, &target)  -> "is there an error of THIS TYPE in the chain?
                                if so, copy it into target."

  var ErrNotFound = errors.New("not found")
  err := fmt.Errorf("loading invoice: %w", fmt.Errorf("order 42: %w", ErrNotFound))

  errors.Is(err, ErrNotFound)   // true  - found through TWO layers
  err == ErrNotFound             // false - only sees the outermost error

  RULE: once wrapping is possible, use errors.Is, never ==.

================================================================================
                 CUSTOM ERROR TYPES
================================================================================

  type ValidationError struct {
      Field, Reason string
  }
  func (e *ValidationError) Error() string {
      return fmt.Sprintf("invalid %s: %s", e.Field, e.Reason)
  }

  Use a sentinel (errors.New) when callers only need to recognize the KIND
  of failure. Use a custom type (struct + Error()) when callers need DATA
  about the failure - extract it with errors.As.

================================================================================
                 THE TYPED-NIL ERROR TRAP
================================================================================

  func broken() *MyError { return nil }   // ❌ concrete pointer return type
  var err error = broken()
  err == nil   // FALSE! the interface holds (*MyError, nil) - non-nil!

  func fixed() error { return nil }       // ✅ interface return type
  var err error = fixed()
  err == nil   // TRUE - untyped nil, interface is (nil, nil)

  ALWAYS declare error, never a concrete error pointer, as a return type.
  (This is Level 15's typed-nil interface gotcha, applied directly.)

================================================================================
                 panic AND recover
================================================================================

  panic("message")   // stops execution, runs defers, unwinds, crashes if
                      // nothing recovers it

  func safe() (err error) {
      defer func() {
          if r := recover(); r != nil {       // ONLY works inside a defer
              err = fmt.Errorf("recovered: %v", r)
          }
      }()
      riskyCall()
      return nil
  }

  panic is for BUGS and impossible states. error is for expected failures -
  bad input, missing files, anything a user could trigger. When in doubt,
  return an error.

================================================================================
                    A SIMPLE EXAMPLE
================================================================================

package main

import (
    "errors"
    "fmt"
)

var ErrNotFound = errors.New("not found")

func find(id int) error {
    if id != 1 {
        return fmt.Errorf("looking up id %d: %w", id, ErrNotFound)
    }
    return nil
}

func main() {
    err := find(42)
    if errors.Is(err, ErrNotFound) {
        fmt.Println("not found:", err)
    }
}

Output:
  not found: looking up id 42: not found

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. THE INTERFACE
   error is one method: Error() string. Any type with it IS an error.

2. CREATING
   errors.New for fixed text, fmt.Errorf for formatted text and wrapping.

3. WRAPPING
   %w links errors into a chain; %v copies text only and breaks the chain.

4. INSPECTING
   errors.Is for sentinel identity, errors.As for typed data extraction.

5. THE TRAP
   Return error, never a concrete error pointer - or nil lies to you.

6. THE ESCAPE HATCH
   panic for bugs, error for everything else. recover() only inside defer.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Ignoring an error
  value, _ := strconv.Atoi(input)

✅ RIGHT
  value, err := strconv.Atoi(input)
  if err != nil { return fmt.Errorf("parsing input: %w", err) }

---

❌ WRONG: Comparing a possibly-wrapped error with ==
  if err == ErrNotFound { ... }

✅ RIGHT
  if errors.Is(err, ErrNotFound) { ... }

---

❌ WRONG: Returning a concrete error pointer type
  func validate() *ValidationError { return nil }

✅ RIGHT
  func validate() error { return nil }

---

❌ WRONG: Panicking for a normal, expected failure
  if !ok { panic("user not found") }

✅ RIGHT
  if !ok { return fmt.Errorf("user not found") }

================================================================================
                      QUICK FAQ
================================================================================

Q: Why doesn't Go have try/catch?
A: Errors are ordinary values, returned like any other value. A function's
   signature tells you it can fail, and if err != nil handles it right
   where the call happens.

Q: When do I use errors.Is vs errors.As?
A: errors.Is asks "is this SPECIFIC value anywhere in the chain?" (sentinels).
   errors.As asks "is there an error of this TYPE anywhere in the chain -
   give it to me so I can read its fields?" (custom types).

Q: Why does err != nil sometimes lie?
A: The typed-nil trap - a function declared to return a concrete error
   pointer type, returning a nil pointer of that type, produces a non-nil
   error interface. Always declare error as the return type.

Q: When is it okay to panic?
A: Almost never in application code. Reserve it for programmer bugs and
   impossible states - not for expected failures like bad input.
