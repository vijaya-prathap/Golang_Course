                      THE BIG PICTURE
================================================================================

Why a Capstone?
  → Every level 1-39 taught ONE skill in isolation
  → Real engineering needs ALL of them working together at once
  → This level is the first time you'll feel what that actually takes

The Architecture (Levels 30 + 31):

  Handler  ──depends on──>  Service  ──depends on──>  Repository (interface)
  (HTTP)                     (rules)                    (in-memory storage)

  Wired together by hand in main.go's buildServer() - the ONE place that
  knows any concrete type. Everything else depends on interfaces.

================================================================================
                    THE 10 MILESTONES
================================================================================

 1. Domain models + Link repository (in-memory, mutex-guarded)
 2. User repository (username uniqueness enforced at storage)
 3. LinkService: URL validation, per-user limit, crypto/rand short codes
 4. UserService: bcrypt password hashing, JWT issue/parse (Level 32)
 5. Handler layer: routes wired to services, tested with stub middleware
 6. REAL JWT auth middleware, replacing the test stub
 7. Structured logging + configuration - catches a REAL bug along the way
 8. Token-bucket rate limiter (bridges Level 39)
 9. main.go wiring + full end-to-end test - catches a SECOND real bug
10. Dockerfile + Kubernetes manifests (Levels 35-36's honesty pattern)

Every milestone with Go code is ACTUALLY RUN - go build, go test, go run,
even real curl commands against a live server. Nothing is hand-computed.

================================================================================
                 A TASTE OF THE ARCHITECTURE
================================================================================

package main

// buildServer is the composition root (Level 31): the ONE place that
// knows how the whole dependency graph fits together.
func buildServer(cfg config.Config, logger *slog.Logger) http.Handler {
    linkRepo := repository.NewInMemoryLinkRepository()
    userRepo := repository.NewInMemoryUserRepository()

    linkService := service.NewLinkService(linkRepo, cfg.CodeLength)
    userService := service.NewUserService(userRepo, cfg.JWTSecret, cfg.TokenTTL)

    linkHandler := handler.NewLinkHandler(linkService)
    authHandler := handler.NewAuthHandler(userService)

    logging := middleware.Logging(logger)
    requireAuth := middleware.RequireAuth(userService)
    limiter := ratelimit.NewLimiter(cfg.RateLimitPerSec, cfg.RateLimitBurst)

    return handler.NewMux(linkHandler, authHandler, logging, requireAuth,
        limiter.Middleware(ratelimit.KeyByRemoteAddr))
}

================================================================================
                 TWO REAL BUGS YOU'LL RECREATE
================================================================================

This level's own authoring hit two genuine bugs while writing its tests -
both left in EXERCISES.md on purpose, because real testing finds real
bugs even in carefully-written code:

  BUG 1 (Milestone 7): t.Setenv("PORT", "") sets PORT to an EMPTY STRING,
  which os.LookupEnv correctly reports as PRESENT, not unset - so a
  default value never applied. The fix was in the TEST, not the code.

  BUG 2 (Milestone 9): closing an HTTP response body without reading it
  first prevents connection reuse, which meant a rate limiter keyed by
  RemoteAddr got a BRAND NEW client "identity" on every single request in
  a test loop - so it never throttled anything. The fix: drain the body
  before closing it.

Both are walked through step by step, with the real failing output shown
BEFORE the fix, exactly as they happened during this level's own build.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Coding straight into handlers without designing the API first
  → discovers the request/response shape by accident, three refactors in

✅ RIGHT: Write the endpoint table and data model FIRST (README.md Section 3)

---

❌ WRONG: Business logic leaking into the Handler
  func (h *LinkHandler) CreateLink(w, r) {
      if !strings.HasPrefix(url, "http") { ... }  // validation doesn't belong here!
      h.repo.Create(...)                           // skips the Service entirely!
  }

✅ RIGHT: Handler decodes and delegates; Service validates and decides

---

❌ WRONG: Writing all 10 milestones, then testing once at the very end
  → both real bugs above would be MUCH harder to isolate this way

✅ RIGHT: Run go test after every single milestone, exactly as EXERCISES.md does

---

❌ WRONG: Over-scoping - "my capstone will also have an admin dashboard,
  OAuth, analytics, and email notifications..."

✅ RIGHT: One resource, fully built, fully tested, fully shippable - small
  and complete beats large and half-finished

================================================================================
                      QUICK FAQ
================================================================================

Q: Why in-memory storage instead of a real database?
A: Level 30's own argument: the whole point of the Repository interface is
   that storage is swappable. Keeping it in-memory keeps this level's
   storage layer 100% offline; swapping in Level 29's SQLite approach
   later is a pure drop-in behind the same interface.

Q: Why does this level use bcrypt and JWT if the course avoids network
   dependencies elsewhere?
A: Level 32 already established this exact, clearly-flagged exception -
   both are pinned versions, fetched once, cached after that.

Q: Why is only ONE endpoint rate-limited and only ONE endpoint auth-protected?
A: Because that's the honest answer to "which endpoint needs this?" -
   GET /{code} is the one the whole internet can hit; POST /shorten is the
   one that creates data on someone's behalf. Protecting everything
   uniformly would be less realistic, not more secure.

Q: Are the Docker/Kubernetes steps actually verified?
A: No - and the materials say so explicitly, following the exact honesty
   pattern Levels 35 and 36 already established for this environment.
