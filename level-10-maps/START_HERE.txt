================================================================================
                      THE BIG PICTURE
================================================================================

What is a Map?
  → An unordered collection of key-value pairs
  → Implemented internally as a hash table - fast lookup, insert, delete
  → No guaranteed order (you already saw this in Level 6)

Why Maps Matter:
  → Almost every real program needs fast lookups by some kind of key -
    counting words, indexing records, caching results, tracking sets
  → Maps are Go's single built-in tool for all of that

================================================================================
                 THREE WAYS TO CREATE A MAP
================================================================================

1. MAP LITERAL (ready immediately)

  ages := map[string]int{"Alice": 30, "Bob": 25}

2. make() (empty, ready immediately)

  scores := make(map[string]int)
  scores["Charlie"] = 88

3. var (THE DANGEROUS ONE - gives you nil!)

  var scores map[string]int
  fmt.Println(scores == nil) // true

A nil map looks empty and reads safely, but you CANNOT write to it yet.

================================================================================
                 THE nil MAP GOTCHA (most important rule!)
================================================================================

  READING from a nil map is completely safe:

    var m map[string]int
    value := m["anything"]   // 0, no panic

  WRITING to a nil map PANICS:

    var m map[string]int
    m["key"] = 1             // panic: assignment to entry in nil map

  This is Go's real, exact panic message - verified by actually running it:

    panic: assignment to entry in nil map

    goroutine 1 [running]:
    main.main()
            /path/to/main.go:5 +0x34
    exit status 2

  THE FIX: always initialize before writing.

    m := make(map[string]int)   // or m := map[string]int{}
    m["key"] = 1                 // fine now

================================================================================
                 THE comma-ok IDIOM, IN DEPTH
================================================================================

A bare index can't tell "absent" from "present but zero":

  stock := map[string]int{"bananas": 0}
  stock["bananas"]   // 0 - present, genuinely zero
  stock["grapes"]    // 0 - absent! Same output, totally different meaning!

comma-ok tells you the truth:

  qty, ok := stock["bananas"]  // qty=0,  ok=true  -> present
  qty, ok  = stock["grapes"]   // qty=0,  ok=false -> absent

  if v, ok := m[k]; ok {
      fmt.Println("found:", v)
  }

Use comma-ok any time zero is a value your program might legitimately store.

================================================================================
                 MAP KEY REQUIREMENTS
================================================================================

Map keys must be COMPARABLE (usable with == and !=):

  VALID:   int, string, bool, float64, arrays, structs (comparable fields),
           pointers
  INVALID: slices, maps, functions

Trying an invalid key doesn't even compile. Verified, real compiler output:

  bad := map[[]int]string{}
  // ./main.go:6:13: invalid map key type []int

================================================================================
                 MAPS AS SETS
================================================================================

Go has no built-in Set type, but a map fakes one perfectly:

  // map[T]bool - simple, costs 1 byte per entry
  set := map[string]bool{"a": true}

  // map[T]struct{} - the idiomatic, ZERO-byte-per-entry set
  set := map[string]struct{}{"a": {}}
  _, inSet := set["a"]

struct{} is the empty struct - it holds no data and occupies zero bytes,
verified with unsafe.Sizeof(struct{}{}) == 0.

================================================================================
                 MAPS OF STRUCTS: THE ADDRESSABILITY GOTCHA
================================================================================

  type Player struct{ Score int }
  players := map[string]Player{"a": {}}

  players["a"].Score = 10
  // DOES NOT COMPILE! Verified, real compiler output:
  // ./main.go:15:2: cannot assign to struct field players["a"].Score in map

Why: map values aren't addressable - players["a"] behaves like a copy, and Go
won't let you mutate a field of something it can't guarantee is the real
stored value.

  FIX 1: read, modify, reassign the whole struct
    p := players["a"]; p.Score = 10; players["a"] = p

  FIX 2: use a map of pointers instead
    ptrs := map[string]*Player{"a": {}}
    ptrs["a"].Score = 10   // compiles fine!

================================================================================
                 NESTED MAPS
================================================================================

  m := make(map[string]map[string]int)

  m["missing"]["x"]        // safe read: 0, no panic (inner map is nil)
  m["a"]["b"] = 1           // PANIC if m["a"] was never created!

  // The safe pattern: guard the inner map first
  if m["a"] == nil {
      m["a"] = make(map[string]int)
  }
  m["a"]["b"] = 1           // fine now

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. THREE WAYS TO CREATE
   literal, make(), var (nil - dangerous!)

2. THE nil ASYMMETRY
   reads are always safe; writes panic on a nil map

3. CRUD
   m[k]=v (create/update), v:=m[k] (read), delete(m,k) (always safe)

4. comma-ok
   v, ok := m[k] - the only reliable way to check presence

5. KEYS
   must be comparable; slices/maps/funcs fail to compile

6. SETS
   map[T]struct{} - zero memory, no ambiguous state

7. STRUCT GOTCHA
   m[k].Field = x doesn't compile for map[K]StructType; use pointers or
   reassign the whole struct

8. NESTED MAPS
   guard the inner map before writing; reading is always safe

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Writing to a nil map
  var m map[string]int
  m["key"] = 1   // panic!

✅ RIGHT
  m := make(map[string]int)

---

❌ WRONG: Bare index to check existence
  if m["key"] != 0 { }   // can't tell absent from stored-zero

✅ RIGHT
  if _, ok := m["key"]; ok { }

---

❌ WRONG: Slice as a map key
  bad := map[[]int]string{}   // invalid map key type []int

✅ RIGHT: use a fixed-size array
  ok := map[[3]int]string{}

---

❌ WRONG: Struct field through a map
  players["a"].Score = 10   // cannot assign to struct field ... in map

✅ RIGHT: reassign the whole struct, or use a map of pointers

---

❌ WRONG: Writing through an uninitialized inner map
  grid := make(map[string]map[string]int)
  grid["a"]["b"] = 1   // panics if grid["a"] was never created

✅ RIGHT: initialize the inner map first

================================================================================
                      QUICK FAQ
================================================================================

Q: Why does reading a nil map work but writing doesn't?
A: A nil map has no hash table allocated. Answering "is this here?" needs no
   storage, so it's always safe. Storing a new entry needs somewhere to put
   it, and Go won't silently allocate that for you.

Q: When do I actually need comma-ok?
A: Whenever the zero value (0, "", false) could legitimately be a value your
   program stores on purpose - comma-ok is the only way to tell "stored zero"
   from "never stored."

Q: Why can't I use a slice as a map key?
A: Map keys must be comparable with ==. Slices (and maps, and functions)
   aren't comparable, so the compiler rejects them.

Q: Why doesn't players["alice"].Score = 10 compile?
A: Map values aren't addressable - players["alice"] behaves like a copy, not
   a real memory location. Reassign the whole struct, or store pointers.

Q: Why does grid["a"]["b"] = 1 panic even though grid isn't nil?
A: grid["a"] (the inner map) can still be nil even if grid itself was made.
   Same nil-map-write rule, one level deeper.
