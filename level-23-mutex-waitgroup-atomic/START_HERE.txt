================================================================================
                 sync.Mutex: THE CRITICAL SECTION
================================================================================

  mu.Lock()
  defer mu.Unlock()   // idiomatic - placed right after Lock()
  counter++           // only ONE goroutine at a time can be here

Verified: an unguarded counter++ lost increments on every one of 5 runs
(976, 962, 947, 958, 945 out of an expected 1000). The mutex-protected
version hit exactly 1000 EVERY time - plain runs AND under `go run -race`
(0 races found). -race IS available in this project's sandbox (needs cgo,
which works here).

================================================================================
                 sync.RWMutex: READERS AND WRITERS
================================================================================

  mu.RLock()   // many goroutines can hold this AT THE SAME TIME
  mu.Lock()    // one goroutine, EXCLUSIVE - no readers, no other writers

RWMutex helps when reads are frequent AND substantial. For trivially
cheap reads, don't assume RWMutex is automatically faster - this level's
own benchmark measured PLAIN MUTEX AS FASTER (13.6ms vs 20ms for 100,000
cheap map-lookup reads) because RWMutex's extra bookkeeping wasn't worth
it here. Measure before assuming.

================================================================================
                 sync.WaitGroup: THE TWO CLASSIC BUGS
================================================================================

BUG 1 - Add() called INSIDE the goroutine (races with Wait):

  for i := 0; i < 5; i++ {
      go func() {
          wg.Add(1)        // WRONG - Wait() below might already be checking
          defer wg.Done()
      }()
  }
  wg.Wait()                // can return with the counter still at 0!

Verified: in 13 total runs of this exact pattern, EVERY run had Wait()
return before any goroutine's Add() executed.

BUG 2 - WaitGroup passed BY VALUE (copies the counter):

  func worker(wg sync.WaitGroup, item string) {  // VALUE param = a COPY
      defer wg.Done()   // decrements the COPY, never the original
  }

`go vet` catches this WITHOUT running anything:
  main.go:11:21: processItem passes lock by value: sync.WaitGroup contains sync.noCopy

Running it anyway produces a REAL, captured deadlock (verified 3 times,
identical every run):

  fatal error: all goroutines are asleep - deadlock!

  goroutine 1 [sync.WaitGroup.Wait]:
  sync.(*WaitGroup).Wait(...)
  main.main()
  exit status 2

FIX for both: call Add() before `go`, and always pass *sync.WaitGroup
(a pointer), never sync.WaitGroup by value.

================================================================================
                 sync/atomic: LOCK-FREE COUNTERS
================================================================================

  var counter atomic.Int64
  counter.Add(1)      // atomically add
  counter.Load()       // atomically read
  counter.CompareAndSwap(0, 5)

Verified: 1000/1000, then 5000/5000, EXACT under concurrent increments,
plain runs AND under -race - no mutex needed anywhere.

ATOMIC vs MUTEX:
  One independent variable (counter, flag, pointer)  → atomic
  Multiple related fields that must move together     → mutex

================================================================================
                 sync.Once: EXACTLY ONE INITIALIZATION
================================================================================

  var once sync.Once
  once.Do(func() {
      // runs EXACTLY once, no matter how many goroutines call once.Do
  })

Verified: 100 concurrent callers, the init function ran exactly 1 time,
and all 100 goroutines received the identical initialized instance.

================================================================================
                 A REAL LOCK-ORDERING DEADLOCK
================================================================================

  func transferAtoB() { mu1.Lock(); mu2.Lock() /* ... */ }
  func transferBtoA() { mu2.Lock(); mu1.Lock() /* ... */ }  // OPPOSITE ORDER!

If A grabs mu1 while B grabs mu2, each then waits forever for the lock
the other is holding. Verified 3 times in this sandbox - EVERY run
deadlocked, and Go's runtime caught it and printed a full goroutine dump
naming exactly which goroutine was stuck on which lock.

FIX: always acquire shared locks in the SAME order, everywhere.

================================================================================
                    KEY CONCEPTS SUMMARY
================================================================================

1. MUTEX
   Lock()/Unlock() bracket a critical section - only one goroutine inside
   at a time. Use defer mu.Unlock() immediately after Lock().

2. RWMUTEX
   RLock()/RUnlock() for concurrent readers, Lock()/Unlock() for
   exclusive writers. Not automatically faster - measure first.

3. WAITGROUP
   Add() before `go`, never inside the goroutine. Always pass by
   pointer, never by value.

4. ATOMIC
   Lock-free operations for ONE independent variable. Multiple related
   fields still need a mutex.

5. ONCE
   Guarantees a function runs exactly once, even under massive
   concurrent calls.

6. DEADLOCKS
   Go's runtime can prove when every goroutine is permanently blocked,
   and crashes with a precise diagnostic dump instead of hanging silently.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Forgetting to unlock on an early return
  a.mu.Lock()
  if bad { return false }   // mutex never unlocked - deadlocks every future caller!
  a.mu.Unlock()

✅ RIGHT
  a.mu.Lock()
  defer a.mu.Unlock()
  if bad { return false }

---

❌ WRONG: Passing a lock by value
  func f(wg sync.WaitGroup) { defer wg.Done() }

✅ RIGHT
  func f(wg *sync.WaitGroup) { defer wg.Done() }

---

❌ WRONG: Add() racing with Wait()
  go func() { wg.Add(1); defer wg.Done() }()

✅ RIGHT
  wg.Add(1)
  go func() { defer wg.Done() }()

---

❌ WRONG: Opposite lock ordering between goroutines
  func a() { mu1.Lock(); mu2.Lock() }
  func b() { mu2.Lock(); mu1.Lock() }   // deadlock risk

✅ RIGHT: Same order everywhere
  func a() { mu1.Lock(); mu2.Lock() }
  func b() { mu1.Lock(); mu2.Lock() }

                      QUICK FAQ
================================================================================

Q: Is it safe to actually run the deadlock exercises?
A: Yes. Both deadlocks in this level are genuine "all goroutines asleep"
   situations that Go's runtime detects and crashes on automatically,
   typically within about 100ms. This was verified multiple times in
   this project's own sandbox - the process always terminates on its own.

Q: Does -race work in this environment?
A: Yes - confirmed working throughout this level. It needs cgo, and cgo
   is available here.

Q: Is RWMutex always better for read-heavy code?
A: No. This level's own benchmark found plain Mutex faster than RWMutex
   for cheap reads. RWMutex pays off when reads are frequent AND
   substantial - measure, don't assume.

Q: Why does a copied WaitGroup deadlock instead of just giving a wrong
   answer?
A: Because Done() only ever decrements the COPY inside the function -
   the original counter the caller is Wait()-ing on never moves, so if
   nothing else is running, that's a permanent, detectable deadlock.
