================================================================================
                      THE BIG PICTURE
================================================================================

What is select?
  → A statement that waits on MULTIPLE channel operations at once
  → Proceeds with whichever one is ready first
  → Looks like a switch, behaves nothing like one

Why select Matters:
  → Level 21 gave you channels, but only for waiting on ONE at a time
  → Real programs wait on several things simultaneously: incoming work,
    a shutdown signal, a timeout - select is how you watch all of them
    with a single statement

================================================================================
                 BASIC select
================================================================================

  select {
  case v := <-ch1:
      fmt.Println("ch1:", v)
  case v2 := <-ch2:
      fmt.Println("ch2:", v2)
  }
  // blocks until AT LEAST ONE case is ready,
  // then runs that case's body

================================================================================
                 RANDOM TIE-BREAKING
================================================================================

  If MULTIPLE cases are ready AT THE SAME TIME, Go picks ONE AT RANDOM.
  It is NOT top-to-bottom like a switch. Verified with a real measurement:

  100,000 trials, both channels pre-filled every time:
    chA fired: 49,986 times (50.0%)
    chB fired: 50,014 times (50.0%)

  Roughly even, every run - case order in the source changes nothing.

================================================================================
                 default: NON-BLOCKING select
================================================================================

  select {
  case v := <-ch:
      use(v)
  default:
      // runs IMMEDIATELY if ch had nothing ready
  }

  WITHOUT default, the select above would BLOCK until ch had something.

================================================================================
                 TIMEOUTS WITH time.After
================================================================================

  select {
  case result := <-work:
      use(result)
  case <-time.After(2 * time.Second):
      fmt.Println("timed out")
  }

  Whichever channel becomes ready first wins - a timeout is just an
  ordinary race between two channels.

================================================================================
                 THE done-CHANNEL CANCELLATION PATTERN
================================================================================

  func worker(done <-chan struct{}, work <-chan int) {
      for {
          select {
          case <-done:
              return
          case w := <-work:
              process(w)
          }
      }
  }

  close(done) tells EVERY goroutine watching it to stop, on their very
  next select. This is the direct, hand-rolled ancestor of Go's context
  package (a later level formalizes exactly this pattern).

================================================================================
                 THE time.After LEAK GOTCHA
================================================================================

  ❌ LEAKY: a brand-new timer is created and abandoned every iteration
    for {
        select {
        case v := <-ch:
            use(v)
        case <-time.After(d):
            onTimeout()
        }
    }

  ✅ BETTER: one timer, reused
    timer := time.NewTimer(d)
    defer timer.Stop()
    for {
        if !timer.Stop() {
            select { case <-timer.C: default: } // drain a pending fire
        }
        timer.Reset(d)
        select {
        case v := <-ch:
            use(v)
        case <-timer.C:
            onTimeout()
        }
    }

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. SELECT
   Waits on multiple channel operations, proceeds with whichever is
   ready first. Not a switch - order in the source means nothing.

2. TIE-BREAKING
   Multiple ready cases -> Go picks ONE AT RANDOM, verified with a
   real 100,000-trial measurement landing near 50/50.

3. DEFAULT
   Makes select non-blocking - runs instantly if nothing else is ready.

4. TIMEOUTS
   case <-time.After(d): as a select arm bounds any wait.

5. CANCELLATION
   A done channel, closed once, is a broadcast every select-ing
   goroutine notices immediately - the ancestor of context.

6. NIL CHANNELS
   A nil channel's case is never ready - the clean way to disable
   one branch of a select at runtime.

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Forgetting default makes select block
  select {
  case v := <-ch:
      use(v)
  }   // BLOCKS if ch has nothing ready - no default to fall back on

✅ RIGHT: Add default for a non-blocking check
  select {
  case v := <-ch:
      use(v)
  default:
      // handle "nothing ready" here
  }

---

❌ WRONG: Assuming the first case wins when both are ready
  select {
  case v := <-ch1:  // NOT guaranteed to win just because it's listed first
  case v := <-ch2:
  }

✅ RIGHT: Understand ties are broken randomly - if you need real
  priority, check the priority channel first with its own
  non-blocking select/default, THEN fall through to a blocking select

---

❌ WRONG: time.After inside a loop, called every iteration
  for {
      select {
      case v := <-ch:
          use(v)
      case <-time.After(d):
          onTimeout()
      }
  }

✅ RIGHT: time.NewTimer once, Stop()/Reset() each pass (see above)

---

❌ WRONG: No way to ever stop an unbounded select loop
  for {
      select {
      case v := <-work:
          process(v)
      }
  }   // runs forever - only way out is killing the process

✅ RIGHT: Always include a done case, counter, or timeout

================================================================================
                      QUICK FAQ
================================================================================

Q: Is select just a switch for channels?
A: No - a switch compares a value against cases top to bottom. select
   waits on channel operations and, when several are ready at once,
   picks one AT RANDOM. Order in the source has no effect.

Q: What happens if nothing is ready and there's no default?
A: select blocks until at least one case becomes ready - same as a
   single channel operation would.

Q: Why does time.After in a loop matter if the output looks the same?
A: Every call creates a brand-new timer that isn't reclaimed until it
   fires. Fine for a few calls; wasteful in a loop that runs many times.
   time.NewTimer with Stop()/Reset() reuses one timer instead.

Q: Why would a closed channel's case ever be useful in select?
A: That's exactly how done-channel cancellation works - closing done
   makes its case permanently ready, so every watching goroutine
   notices at once. The risk is only an UNBOUNDED loop that keeps
   hitting that case without ever checking ok and exiting.

Q: What's a nil channel good for?
A: Its case is never ready - assigning nil to a channel variable is
   how you disable one branch of a select at runtime, cleanly.
