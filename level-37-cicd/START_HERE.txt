================================================================================
                      THE BIG PICTURE
================================================================================

What is CI/CD?
  → CI (Continuous Integration): every push/PR is automatically built and
    tested. Problems get caught in minutes, on the exact change that
    introduced them - not weeks later, tangled up with everyone else's work.
  → CD (Continuous Delivery/Deployment): once a change passes CI, it's
    automatically packaged and, depending on how far you take it,
    automatically shipped to production.

Why It Matters:
  → Without it, "please remember to run the tests before merging" is a
    request, not a guarantee - and guarantees are what production systems
    actually need.

================================================================================
                 GITHUB ACTIONS: THE FOUR CONCEPTS
================================================================================

1. WORKFLOW - a YAML file under .github/workflows/, auto-discovered by GitHub

2. TRIGGER (on:) - the event that starts a run

  on:
    push:
      branches: [main]
    pull_request:
      branches: [main]

3. JOB - an independent unit of work; jobs run in PARALLEL by default,
   unless linked with needs:

4. STEP - one action within a job, run sequentially; either `uses:` a
   pre-built action, or `run:` a raw shell command

  jobs:
    build-and-test:
      runs-on: ubuntu-latest          <- the RUNNER
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-go@v5
          with:
            go-version: '1.23'
        - run: go build ./...
        - run: go vet ./...
        - run: go test ./...

================================================================================
                 THE gofmt GOTCHA (LEARN THIS NOW)
================================================================================

gofmt -l . lists files that need reformatting - but it STILL exits 0, even
when it lists something. Confirmed for real in this environment:

  $ gofmt -l .
  main.go
  $ echo $?
  0

A CI step that trusts this exit code will NEVER fail, no matter how
mangled the formatting is. The fix: check whether the OUTPUT is empty,
not the exit code.

  - name: Check formatting (gofmt)
    run: |
      unformatted=$(gofmt -l .)
      if [ -n "$unformatted" ]; then
        echo "$unformatted"
        exit 1
      fi

================================================================================
                    THE QUALITY GATE SEQUENCE
================================================================================

Run cheapest/fastest checks first, so a broken build fails in seconds:

  1. gofmt   - check for EMPTY output (the gotcha above)
  2. build   - go build ./...
  3. vet     - go vet ./...
  4. lint    - golangci-lint run ./...
  5. test    - go test -race -cover ./...   (slowest - -race adds overhead)

A `docker` job, gated with `needs: build-and-test`, builds and pushes the

A `deploy` job, gated with `needs: docker`, runs `kubectl set image` and
`kubectl rollout status` - the scripted equivalent of the rolling update
you did by hand in Level 36.

Both are illustrative sketches here (no real registry or cluster in this
sandbox) but are correct per their documented, stable behavior.

================================================================================
                    DEPLOYMENT STRATEGIES AT A GLANCE
================================================================================

  ROLLING:     replace old instances a few at a time - no extra infra,
               moderate rollback speed
  BLUE-GREEN:  deploy fully to an idle environment, flip traffic at once -
               instant rollback, needs double the infrastructure
  CANARY:      send a small % of traffic to the new version first - small
               blast radius, needs traffic-splitting + monitoring

================================================================================
                      KEY CONCEPTS SUMMARY
================================================================================

1. CI vs CD
   CI = auto build+test every change. CD = auto package/ship what passed.

2. WORKFLOW ANATOMY
   on: (trigger) -> jobs: (parallel, or needs:-ordered) -> steps: (run/uses)

3. THE GATE SEQUENCE
   gofmt (check OUTPUT!) -> build -> vet -> lint -> test -race -cover

4. NEVER HARDCODE SECRETS
   Always ${{ secrets.NAME }}, configured in repo settings - never a
   literal credential in the YAML file.

5. DEPLOYMENT STRATEGIES
   Rolling (default, gradual) / Blue-Green (instant rollback, double infra)
   / Canary (smallest blast radius, needs traffic-splitting)

================================================================================
                    COMMON MISTAKES TO AVOID
================================================================================

❌ WRONG: Trusting gofmt -l .'s exit code alone
  gofmt -l .                       # exits 0 even when files are listed!

✅ RIGHT: Check for empty output
  test -z "$(gofmt -l .)"

---

❌ WRONG: Unpinned action versions
  uses: actions/checkout@main      # can change behavior with no repo change

✅ RIGHT
  uses: actions/checkout@v4

---

❌ WRONG: Secrets hardcoded in the workflow file
  run: docker login -u admin -p hunter2

✅ RIGHT
  run: docker login -u ${{ secrets.DOCKERHUB_USERNAME }} -p ${{ secrets.DOCKERHUB_TOKEN }}

---

❌ WRONG: No dependency caching
  cache: false                     # every run re-downloads everything

✅ RIGHT
  cache: true

---

❌ WRONG: Testing only on merge to main
  on:
    push:
      branches: [main]

✅ RIGHT: Test every PR before it can even be merged
  on:
    push:
      branches: [main]
    pull_request:
      branches: [main]

================================================================================
                      QUICK FAQ
================================================================================

Q: Why does gofmt -l . exit 0 even when it lists files?
A: gofmt -l only returns non-zero on a genuine parse error, never merely
   because a file needs reformatting - confirmed for real in this
   environment. Check its OUTPUT, not its exit code.

Q: Was any of this actually run on GitHub?
A: No - there's no git repository anywhere in this course, so nothing was
   pushed to real GitHub infrastructure. Every Go command was genuinely run
   locally, and every workflow YAML file was validated as syntactically
   correct - but a real, GitHub-hosted run was never exercised.

Q: Do I need Docker or a Kubernetes cluster to complete this level?
A: No. Like Levels 35 and 36, the Docker-push and Kubernetes-deploy
   sections are illustrative sketches. Everything else - the Go commands
   and the workflow YAML - is fully real and something you can verify on
   your own machine right now.

Q: What's the difference between CI and CD?
A: CI = automatically build and test every change. CD = what happens after
   CI passes: Continuous Delivery usually still has a human click
   "release"; Continuous Deployment ships with no human in the loop.
